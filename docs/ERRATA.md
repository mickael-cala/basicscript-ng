## E1

**Symptôme** — `include/error.bas` annonce dans son en-tête « automatically
generated by the program generrh.pl using the error code definition file
errors.def ». Ni `generrh.pl`, ni `errors.def` ne sont dans le dépôt.

**Cause** — le fichier vient de la distribution d'origine ; le générateur
faisait partie de la chaîne Perl abandonnée lors de l'aplatissement.

**Conséquence** — si un code d'erreur change dans `src/errcodes.c`, le
fichier `.bas` ne suivra pas tout seul. C'est un contrat à tenir à la main.

**Travail** — soit réécrire un générateur Python à partir de `errcodes.h`
(une centaine de lignes), soit ajouter un test qui compare les deux. Voir
[ROADMAP](ROADMAP.md#p2--modules).

**Travail** — un `pod2md.py` du dépôt (voir
[ROADMAP](ROADMAP.md#p4--documentation)).

## E3

**Symptôme** — `python tests/run.py` annonce « 20/20 » alors que `tests/`
contient quarante-cinq `.bas` ; `--modules` en lance dix-neuf sous Windows,
dix-huit sous Linux/macOS.

**Cause** — sous Windows, les autres exigent un module non construit
(`dyc.bas`, `dyc_abi.bas`, `dyc_bench.bas`, `dyc_com.bas`, `dyc_fixture.bas`,
`odbc.bas`), l'ABI 32 bits de `dyc`, des privilèges (`win_hardlink.bas`),
sont un essai de fuite (`mt_leak.bas`), sont spécifiques à Windows
(`manuel.bas`), demandent le module `unix`, absent sous Windows
(`unix.bas`), ou passent par le mode `--cgi-post` (`cgi_post.bas`,
`cgi_upload.bas`, `err_runtime.bas`, `err_load.bas`, `err_module.bas`,
`err_pending.bas` et `err_partial.bas`).

**Conséquence** — « 20/20 » mesure le coeur : onze scripts exécutés et neuf
refus à l'analyse (`refus_directory`, `refus_pause`, `refus_fork`,
`refus_sqr`, `refus_operateur`, `refus_cv`, `refus_mk`, `refus_slif_for`,
`refus_slif_mix`) ; « 19/19 » (Windows) ou
« 18/18 » (Linux/macOS) avec `--modules` ajoute les modules construits, pas
les autres. Aucun de ces chiffres ne dit « tout va bien ».

**Travail** — construire les modules restants (P2 et P6 du
[ROADMAP](ROADMAP.md)) puis les ajouter au jeu.

**Précision utile** — ScriptBasic rend 0 même sur une erreur de syntaxe ou
d'include. Le lanceur traite donc comme échec un code non nul, une ligne
`ECHEC` ou un message `error &H…` ; le code de sortie seul ne prouve rien.

## E4

**Symptôme** — `tests/upstream/` (32 `.bas`) n'était jamais lancé.

**Cause** — c'est la suite d'origine, reprise telle quelle le 2026-10-23 :
elle suppose des modules, des chemins Windows, un réseau ou une saisie, et
certains scripts sont des démonstrations sans assertion.

**Conséquence** — matière première pour écrire des tests, pas un jeu
exécutable en l'état. Un lancement naïf des 32 fichiers produirait des échecs
qui ne disent rien sur le portage (`test_ext_trial.bas` demande un module qui
n'existe plus, `testwin.bas` écrit dans le registre, `testcio.bas` boucle sur
une console interactive).

**Parade** — le fichier `tests/upstream/MANIFEST.tsv` décrit les 32 `.bas`
et `tests/run.py --upstream` n'exécute que ceux qui ont un sens : tests du
coeur et modules réellement construits. `--upstream-all` ajoute les essais
longs et les diagnostics. Mesure du 2026-10-24, Windows x64 et Linux x64,
avec les modules construits : **12 lancés, 0 échec, 20 sautés** ; avec
`--upstream-all`, 15 lancés et 17 sautés. Les 17 sauts sont justifiés un
par un dans le manifeste (réseau externe, module absent, interaction,
registre, pile du parseur).

**Périmètre** — E4 ne concerne **que** les 32 `.bas` de `tests/upstream/`.
Il ne dit rien des formes historiques ni des `.jam` :

- **`--standalone`**, **`--stndlone`** et **`--libscriba`** sont désormais
  des cibles de `build.py` ; leurs sorties sont vérifiées à part par
  `tests/run.py --standalone` et `--stndlone`, pas par E4.
- **`basicc`** et **`basiccmd`** ont été retirés le 2026-10-24 : c'étaient
  des doublons historiques, remplacés par `stndlone` et `scribacmd`.
  **`basicdll`** ([E21](#e21)) et **`scribawx`** ([E22](#e22)) ont été
  retirés le même jour : le premier n'avait pas d'implémentation, le second
  demandait wxWidgets. E4 ne concerne aucune de ces quatre formes. Le détail
  est dans
  [PROGRAMMES.md § 2](PROGRAMMES.md#2-les-autres-programmes-et-formes-du-dépôt).
- **Les autres sources sans cible** (26 `.c` après le retrait de
  `tools/fork.c`) sont auditées une par une dans
  [PROGRAMMES.md § 2.2](PROGRAMMES.md#22-sources-sans-cible--décision-daudit-2026-10-24) :
  aucune n'est un test upstream, et aucune n'entre donc dans E4.
- **Les 20 `manual.texi.jam`** ne sont ni des programmes ni des tests :
  c'étaient des modèles de manuel. Les **20/20 sont supprimés**, aucun ne reste
  dans `src/extensions/`, et ils ne doivent pas revenir ([E2](#e2)). Il ne
  subsiste que deux `.jam` de **données** dans `examples/sibawa/`, hors build ;
  le remplacement prévu est `pod2md.py`, pas Jamal.

## E6

**Symptôme** — `curl` récent affiche `Received HTTP/0.9 when not allowed` et
n'affiche aucun corps, alors que le script s'est bien exécuté (visible dans
`logs/hit.txt`).

**Cause** — `sbhttpd` n'ajoute **pas** d'en-tête : c'est le script qui doit
écrire sa ligne de statut et ses `Content-type`. Un script qui commence par
`print "bonjour\n"` produit une réponse que HTTP/1.x n'autorise pas.

**Correctif (2026-10-26, phase 7)** — le serveur parle désormais
HTTP/1.x lui-même : quand la première ligne du script n'est ni
`Status:` ni `HTTP/`, toute la réponse est accumulée puis émise
avec `HTTP/1.1 200 OK`, `Content-Type: text/html` et
`Content-Length` exact. Un script qui écrit son `Status:` garde le
passthrough d'origine, et `servers.autoheaders 0` dans la
configuration restaure l'ancien comportement. Les pages d'erreur
du serveur (E23-E25) ne se doublent pas : toute écriture directe
fait retomber le drapeau de première ligne.

**Parade historique (avant correctif) — deux possibilités, au choix :

```
print "HTTP/1.0 200 OK\nContent-type: text/plain\n\nbonjour\n"
```

ou, côté client, `curl --http0.9`. Le `webtest/404.bas` du dépôt montre la
première forme ; `webtest/index.bas` montre la seconde (corps seul, à lire
avec `--http0.9`).

## E7

**Symptôme** — `python build.py --target linux-x64 --httpd` échoue :

```
src/httpd.c:468:32: error: call to undeclared function 'inet_addr'
src/httpd.c:493:29: error: call to undeclared function 'inet_ntoa'
src/variations/httpd/websrv.c:518:25: error: call to undeclared function 'inet_addr'
src/variations/httpd/websrv.c:600:15: error: call to undeclared function 'stricmp'
src/variations/httpd/websrv.c:814:28: error: call to undeclared function 'inet_ntoa'
src/variations/httpd/websrv.c:1321:3: error: call to undeclared function 'strnicmp'
```

**Cause** — deux choses que TCC tolérait et que clang refuse :

1. `inet_addr` / `inet_ntoa` demandent `<arpa/inet.h>`, que les deux fichiers
   n'incluent pas (sous Windows, `winsock2.h` les déclare) ;
2. `stricmp` / `strnicmp` sont des noms Microsoft ; sous Unix ce sont
   `strcasecmp` / `strncasecmp`.

**Correction** (2026-10-23) — six lignes dans les deux fichiers, sous
`#ifndef WIN32` : `<arpa/inet.h>` et les deux `#define`. Une septième erreur
apparaissait ensuite, dans `variations/httpd/service.c` : `static dummy()`
est une définition K&R que le C23 refuse ; elle devient
`static void dummy(void)`. Sous Unix ce fichier n'est qu'une unité vide
(le mode service est Windows), d'où l'absence d'autre correction.

**Vérifié** — `python build.py --target linux-x64 --httpd` réussit, et
`sbhttpd` lancé depuis la racine avec `SCRIBACONF=dist/linux-x64/scriba.conf`
répond `sbhttpd OK` à `curl --http0.9 http://127.0.0.1:18080/index.bas`
depuis WSL. Le mode service et les autres cibles Unix ne sont pas testés.

**À noter** — le reste du serveur était déjà portable : `websrv.c` a ses deux
chemins (`CreateProcess`/service sous Windows, `fork`/daemon/signaux sous
Unix) et `thread.c` bascule sur `pthread` hors Windows.

## E8

**Symptôme** — compiler le C produit par `scriba -C` échoue :

```
hello_gen.c:29:1: error: type specifier missing, defaults to 'int'
hello_gen.c:29:30: error: call to undeclared function 'stndlone'
```

**Cause** — le générateur écrivait du C d'avant 1999 : `main(...)` sans type
de retour, et un appel à `stndlone()` sans déclaration (`stndlone.h` était
vide).

**Correction (2026-10-23)** — `builder.c` écrit `int main(...)` et le prototype
de `stndlone` dans le fichier généré ; `stndlone.c` et `stndlone.h` donnent le
type `int`. Le C produit se compile désormais en C23, sans option de
compatibilité ni `-include` :

```
zig cc -target x86_64-windows-gnu -std=c23 -DWIN32 -O2 \
       -c hello_gen.c -o hello_gen.o
```

Vérifié : le binaire lié ensuite s'exécute et affiche le résultat du
programme.

**Complément (2026-10-24)** — le C généré définissait aussi
`char **_environ;`. Sous UNIX, `stndlone.c` et `libscriba.c` le définissent
déjà : le lien échouait sur `duplicate symbol: _environ`. La définition a été
retirée de `builder.c` ; elle appartient au runtime, pas au bytecode.

**Reste** — aucun. `basicc.c` et `basiccmd.c` portaient encore un `main()`
sans type et échouaient en C23 ; ils ont été retirés le 2026-10-24, remplacés
par `stndlone` et `scribacmd`. Le C généré, `stndlone.c` et `libscriba.c` se
compilent en C23.

## E9

**Symptôme** — après E8, le lien échoue :

```
lld-link: error: duplicate symbol: StaticallyLinkedModules
>>> defined at lmt_none.o
>>> defined at stndlone.o
```

**Cause** — `stndlone.c` apporte **sa** liste `StaticallyLinkedModules`, et
`lmt_none.c` la sienne. De plus `scribacmd.o` apporte un `main`, comme le C
généré.

**Parade** — au lien, écarter `variations_standard_scribacmd.o` **et**
`lmt_none.o`, et ajouter `stndlone.o` + le `.o` du C généré. C'est exactement
ce que fait la recette de [REPRISE.md](REPRISE.md#4-fabriquer-un-exécutable-autonome).

## E10

**Symptôme** — `dyc` ne compile pas en 64 bits : `use of undeclared
identifier 'pModuleObject'`.

**Cause** — `dyc` appelle des fonctions C par la **pile** (`DynaCall`), ce qui
est une convention d'appel 32 bits. Le module est marqué `notunix.txt` et le
portage TCC le filtrait déjà par `ARCH 32`.

**Conséquence** — sous Windows x86 il fonctionne (campagne TCC) ; en 64 bits
il n'existe pas. Ne pas essayer de le « réparer » en changeant un cast : ce
serait un autre module.

## E11

**Symptôme** — `odbc/interface.c:227` : `incompatible pointer types passing
'SQLINTEGER *' (aka 'long *') to parameter of type 'SQLLEN *'`.

**Cause** — en 64 bits, `SQLLEN` est un `long long` et `SQLINTEGER` un `long`.
Le code passe l'adresse de l'un à une fonction qui attend l'autre.

**Travail** — une variable `SQLLEN` locale et une conversion explicite aux
endroits signalés. Le module reste Windows (le gestionnaire ODBC est dans le
système).

## E12

**Symptôme** — `unix/interface.c` : `call to undeclared function 'fork'`, puis
`'chmod'`, puis `'memcpy'`.

**Cause** — `unix` (ex-`ux`) est le module Unix (fork, chmod) ; il suppose
`unistd.h`, `sys/stat.h` et `string.h` déjà inclus, ce que ni le build Windows
ni les options communes des modules ne faisaient.

**Conséquence** — le module ne se compile que pour Linux/macOS, ce qui est
normal, mais il faut lui donner ses en-têtes. `build.py` ajoute désormais
`-include unistd.h -include sys/stat.h` pour ce module seul ; `string.h` vient
de `COMMON`. Vérifié : `unix.so` se charge et `unix::chmod` s'exécute sous
Linux x64 (`tests/unix.bas`).

## E15

**Symptôme** — `sbhttpd` lancé depuis un dossier sans `logs/` se termine
immédiatement, sans message, code de sortie 0.

**Cause** — `AppStart` échoue à ouvrir le fichier pid (`logs/pid.txt`)
déclaré par `scriba.conf.lsp`, et le programme quitte sans rien dire.

**Parade** — créer `logs/` (il est dans `.gitignore`) et lancer depuis un
dossier où `scriba.conf` est trouvable : sous Windows, le fichier est cherché
**à côté de l'exécutable** ; sous UNIX, c'est `SCRIBACONF` (voir
[E19](#e19)). Les chemins `webtest/`, `logs/` sont eux relatifs au
**répertoire courant**.

Depuis la racine du dépôt :

```sh
mkdir -p logs
./dist/windows-x64/sbhttpd.exe &
curl --http0.9 http://127.0.0.1:18080/index.bas
```

Arrêt : supprimer `logs/pid.txt` (le thread de garde s'arrête seul) ou tuer le
PID qui y est écrit.

## E16

Les programmes de `examples/` sont ceux de la distribution : beaucoup font
`import mysql.bas`, `import gd.bas`, `import curl.bas`… et ne peuvent donc
pas tourner tant que ces modules ne sont pas construits. Depuis que `cgi`
est un module (`build.py --modules`), ceux qui ne demandent que lui —
`examples/cgi-bin/echo.bas` par exemple — peuvent désormais se lancer. Les
autres restent utiles comme corpus de lecture et comme tests à venir.

## E17

Deux catégories de scripts ne sont pas portables en l'état :

- `tests/manuel.bas` — vérifie des chemins, des répertoires et `waitpid` :

## E18

**Symptôme** — sous Linux x64, `tests/re.bas` affichait
`nombre de groupes : 224` au lieu de 1, puis mourait sur
`malloc(): unaligned tcache chunk detected`. Les mêmes sources passaient sous
Windows x86 et x64.

**Cause** — l'édition de liens dynamique, pas le code du module. Le moteur de
Henry Spencer définit `regcomp`, `regexec`, `regerror` et `regfree` ; la libc
définit les mêmes noms. Une bibliothèque chargée par `dlopen` résout ses
références dans la portée globale, où la libc vient avant elle : les appels de
`interface.c` partaient donc dans **la libc de glibc**, qui écrivait une
`regex_t` de glibc (48 octets et plus) dans une `regex_t` de Spencer
(32 octets). D'où `re_nsub` lu à l'offset d'un autre champ, et corruption du
tas. Sous Windows il n'y a pas de `regcomp` dans la CRT : le problème ne
pouvait pas apparaître, ce qui rend le piège dépendant de la plateforme.

**Parade** — deux moitiés, dans le dépôt :

1. `src/basext.h` : hors Windows, `DLL_EXPORT` vaut
   `__attribute__((visibility("default")))` au lieu de rien. La macro marque
   exactement ce qu'un module doit exposer (`versmodu`, `bootmodu`, les
   fonctions `besFUNCTION`/`besCOMMAND`).
2. `build.py` : les modules se compilent avec `-fvisibility=hidden`, donc
   `regcomp` et compagnie ne sont plus exportés ni détournables — les appels
   internes se lient à la définition du module.

**Vérifié** — après correction : `re` passe sur Windows x86, Windows x64 et
Linux x64, et la table des symboles dynamiques de `re.so` ne contient plus que
`versmodu`, `bootmodu`, `finimodu` et les fonctions du BASIC (`match`,
`dollar`, `format`…) — plus aucun `regcomp`. Un module futur
qui exposerait une fonction hors `besFUNCTION`/`besCOMMAND` la verrait cachée :
c'est voulu, et c'est écrit dans [MODULES.md § 6](MODULES.md#6-construire-les-modules-aujourdhui).

## E19

**Symptôme** — sous Linux, `./dist/linux-x64/scriba tests/hash.bas` répond
`error &H10: The requested module can not be loaded`, alors que
`dist/linux-x64/modules/hash.so` existe et que `dlopen` l'ouvre très bien.

**Cause** — la configuration n'est pas trouvée. Sous Windows
`cft_GetConfigFileName` cherche `scriba.conf` à côté de l'exécutable ; sous
UNIX (`src/scriba.h`) il n'y a que deux sources : la variable d'environnement
`SCRIBACONF`, puis `/etc/scriba/basic.conf`. Le fichier de `dist/` n'est donc
jamais lu tout seul, et sans configuration la clé `module` est absente : le
module manager n'essaie même pas `modules/`.

**Parade** — désigner la configuration explicitement :

```sh
cd dist/linux-x64
SCRIBACONF="$PWD/scriba.conf" ./scriba ../../tests/hash.bas
```

`tests/run.py` le fait pour les cibles Linux/macOS, et se place dans
`dist/<cible>` pour que les clés relatives `modules/` et `modules/include/`
soient résolues. La même règle vaut pour un binaire macOS.

**Ce n'est pas corrigé** — chercher la configuration à côté du binaire sur
toutes les plateformes serait un changement de comportement du produit, pas
du portage. C'est inscrit en P3 du [ROADMAP](ROADMAP.md#p3--serveur-http), avec
le reste de la question des chemins.

## E20

**Symptôme** — `win::RegRead("HKCU\Environment\TEMP")` rend l'erreur
extension-specific 0x00081001 (« clé invalide »), alors que la clé existe.

**Cause** — l'analyseur de ScriptBasic traite l'antislash comme une séquence
d'échappement dans les chaînes : `\E` vaut `E`, `\T` vaut `T`. La chaîne
arrive au module sous la forme `HKCUEnvironmentTEMP`, sans séparateur, et
`ChopHive` ne reconnaît plus la ruche. Mesuré : `print "HKCU\Environment"`
affiche `HKCUEnvironment`, et `"HKCU\\Environment"` aussi (le double
antislash ne rend pas un antislash).

**Parade** — construire le séparateur avec `chr(92)` :

```basic
bs = chr(92)
cle = "HKCU" & bs & "Environment" & bs & "TEMP"
```

C'est ce que fait [tests/win.bas](../tests/win.bas) pour la clé du registre.
La même règle vaut pour tout chemin Windows écrit dans une chaîne BASIC.

**Ce n'est pas un défaut du portage** — c'est le comportement du langage ; il
est documenté ici parce qu'il fait perdre du temps sur les tests du module
`win`.

## E23

**Symptôme** — un POST multipart dont le fichier dépasse `FILE_MAX` (10 Mo)
est bien refusé, mais la réponse surprenait : `scriba -c` sort avec le code
`524296` et la ligne `error 0x00080008`, tandis que `sbhttpd` répondait
`HTTP 200` avec une page d'erreur, donc un client ne pouvait pas distinguer
le refus d'un succès. Aucun script ne s'exécute : le refus tombe pendant le
démarrage du module `cgi`, donc avant la première ligne BASIC. Le même
schéma valait pour `CGI_ERROR_BIG_CONTENT` (`0x00080002`), qui refuse un
corps annoncé au-delà de `CONTENT_MAX`.

**Cause** — trois comportements se cumulent, tous hérités du module :

1. le module lit chaque octet reçu et compare le compteur à `lFileMax`
   (`cgi.c`, `++i > pCO->lFileMax`) ; pour `CONTENT_MAX` il ne lit rien du
   tout : `lContentLength > lContentMax` suffit ;
2. ces refus sont rendus par `besSUB_START`, donc avant que le programme BASIC
   ne voie quoi que ce soit ;
3. `httpd_report` écrivait `HTTP/1.0 200 OK` avant sa page d'erreur, quel que
   soit le code reçu.

**Correction (2026-10-24)** — `httpd_report` reconnaît `CGI_ERROR_FILEMAX`
(`0x00080008`) et `CGI_ERROR_BIG_CONTENT` (`0x00080002`) et, comme le script
n'a encore rien écrit, répond `413 Request Entity Too Large` avec un corps
texte qui porte le même code et le même message qu'avant
(`error 0x0008000x:Extension specific error: program terminated with error`).
Les autres échecs gardent la page HTML, en `500` depuis la seizième passe
(auparavant `200`, ce qui les faisait passer pour des succès). Le statut 413
a été ajouté à
la table `StateMessages` de `httpd.c`, qui n'avait pas cette entrée et aurait
écrit `HTTP/1.0 413` sans phrase.

Le module consomme aussi le reste du corps avant de rendre l'erreur
(`cgi_DrainInput`, borné par `Content-Length` restant). Sans cela, un fichier
nettement plus gros que la limite laisse des kilo-octets non lus dans la
socket : la fermeture envoie un RST et le client perd le 413 qui vient d'être
ecrit. Avec un dépassement d'un seul octet, ces octets étaient déjà dans le
tampon du module, ce qui masquait le problème.

Le cas `CONTENT_MAX` ne consomme rien, volontairement : le module refuse sur
l'en-tête, et lire un corps qu'on vient de juger trop gros annulerait la
protection. Conséquence assumée : un client qui est encore en train d'envoyer
au moment du refus peut voir la connexion se couper avant de lire le 413.

**Pièges associés** —

- `sbhttpd` n'envoie pas ses erreurs au client par défaut :
  `servers.errmsgdest` vaut 2 (journal seul). Sans `errmsgdest 3`, le client
  reçoit une connexion fermée, sans corps ni statut. `tests/run.py
  --cgi-post` ajoute `errmsgdest 3` à sa configuration temporaire pour
  pouvoir lire le 413.
- dans le journal `err.txt`, le code n'apparaît pas tel quel : `httpd_report`
  remplace tout code supérieur à `MAX_ERROR_CODE` par
  `COMMAND_ERROR_EXTENSION_SPECIFIC` avant de l'écrire, d'où `error &H32`.
  Seule la réponse au client porte `0x00080008`.
- en mode externe, `report_report` reçoit un message `NULL` et affiche donc la
  chaîne de format elle-même : `Extension specific error: %s`. Le code est
  justement vérifié par le test, pas ce texte.
- `CONTENT_MAX` vaut aussi 10 Mo : sans `option cgi$contentmax` dans le
  script, un corps de plus de 10 Mo est refusé plus tôt par
  `CGI_ERROR_BIG_CONTENT` (`0x00080002`) et le contrôle de taille de fichier
  n'est jamais atteint. `tests/cgi_upload.bas` relève `cgi$contentmax` à
  20 Mo et laisse `cgi$filemax` à sa valeur par défaut. Un dépassement plus
  large que 20 Mo serait donc refusé par ce premier contrôle.

**Couverture** — `tests/run.py --target <cible> --cgi-post` exécute trois cas
de refus dans les deux modes : `multipart-filemax` (limite + 1 octet),
`multipart-filemax-256k` (limite + 256 Ko) et `contentmax` (corps annoncé à
`CONTENT_MAX + 1`, sans envoi). Tous exigent le code attendu, l'absence de
ligne de succès et, par le serveur, le statut `413`. Le second est le seul à
distinguer une fermeture propre : sans consommation du corps restant, il
échoue sur une réinitialisation de connexion. Le troisième n'envoie pas de
corps et vérifie le refus sur le seul en-tête. La borne a été mesurée : un
fichier de `FILE_MAX` exact passe, `FILE_MAX + 1` est refusé.

## E24

**Symptôme** — une erreur d'exécution dont le code a le bit `0x2` levé
(`0x00080002`, `0x00080003`, `0x00080006`…) produisait une réponse sans
ligne de statut : le client recevait le texte d'erreur comme s'il était la
ligne de statut et levait `BadStatusLine`. Les autres codes recevaient une
page d'erreur complète — en `200` à l'époque, en `500` depuis la seizième
passe.

**Cause** — `HttpProc` appelait
`httpd_report(..., &iErrorCode)` : il passait l'adresse du code d'erreur à la
place du mot de drapeaux. `httpd_report` y teste `REPORT_F_FRST` (`0x2`) et,
quand ce bit est levé, suppose l'en-tête déjà écrit. Un code comme
`0x00080002` porte ce bit : la réponse commençait donc au corps, sans statut
ni `Content-Type`.

**Correction (2026-10-24)** — `HttpProc` utilise une vraie variable
`fErrorFlags`, remise à zéro avant chaque exécution. Le défaut a été trouvé
en couvrant `CGI_ERROR_BIG_CONTENT` ([E23](#e23)), dont le 413 ne partait
pas.

**Portée** — les erreurs de chargement (include absent, erreur de syntaxe)
n'étaient pas touchées : elles sont rapportées par le lecteur, avec ses
propres drapeaux, avant cet appel.

**Couverture** — `tests/run.py --cgi-post` exécute `tests/err_runtime.bas` :
une ouverture de fichier impossible, donc le code 22 (`0x16`), dont le bit
`0x2` est levé. En externe le lanceur exige le code 22 et `error &H16` ; en
interne, un statut `200` et la page d'erreur complète. Reconstruit avec
l'ancien `&iErrorCode`, `sbhttpd` n'envoie aucune ligne de statut et le cas
échoue sur `BadStatusLine` — c'est le contrôle négatif qui valide le test.

Deux cas voisins figent les autres chemins du rapporteur : `err_load.bas`
(`include` introuvable, erreur de chargement rapportée par le lecteur, et en
externe une page CGI sur stderr avec un code de sortie 0) et `err_module.bas`
(`cgi::SaveFile` refusé, code `0x00080000` au-delà de `MAX_ERROR_CODE`, donc
écrit en `0x%08x` avec le message du module). Tous deux exigent un `500` et
la page HTML complète, comme `err_runtime.bas`.

## E25

**Symptôme** — un script qui a commencé sa réponse puis échoue renvoyait un
corps qui contenait une seconde ligne de statut suivie de la page d'erreur :
`debutHTTP/1.0 500 Internal Error`, puis `Content-Type: text/html` et un
`<HTML>` complet. Le client garde le statut déjà reçu, donc la réponse
restait lisible, mais le corps était pollué et le document ouvert par le
script se refermait sur du texte étranger.

**Cause** — `httpd_report` ne décidait d'écrire statut, type et page que sur
`REPORT_F_FRST`, le drapeau du rapporteur lui-même. Ce drapeau dit « ce
rapport est le premier », pas « le script a déjà répondu » : une erreur
survenant après la première ligne du script repassait donc par le bloc
complet, en-têtes compris.

**Correctif** — la condition est lue sur l'état de la sortie du script.
`pfStdOut` retient la première ligne dans `szBuffer` et ne l'envoie qu'au
saut de ligne, en traduisant `Status:` en `HTTP/1.0` ; c'est à cet instant
qu'il fait retomber `FirstHeaderLine`. Tant que ce drapeau est levé, aucun
octet n'est parti : le statut peut encore être choisi, même si une ligne
incomplète attend dans le tampon. Une fois retombé, la réponse a commencé et
le rapporteur n'ajoute plus qu'un saut de ligne puis le diagnostic — ni
statut, ni `Content-Type`, ni page HTML. Le corps garde le type que le script
a annoncé.

**Couverture** — deux cas de `--cgi-post`, chacun dans les deux modes.
`tests/err_partial.bas` écrit sa ligne de statut et `debut`, puis échoue : en
interne le lanceur exige `200` et interdit `HTTP/1.0`, `<HTML>` et
`Content-Type: text/html` dans le corps (`forbid_httpd`) ; en externe il
interdit `<HTML>` et `Content-Type: text/html` (`forbid`).
`tests/err_pending.bas` est le contrôle négatif : sa première sortie n'a pas
de saut de ligne, donc rien n'est parti et le serveur doit encore répondre
`500` avec la page complète. Traiter un tampon non vide comme une réponse
commencée supprimerait la ligne de statut et rendrait la réponse illisible —
le défaut d'[E24](#e24) par un autre chemin ; le lanceur l'a mesuré
(`requete POST impossible`) avant que la condition ne soit resserrée sur
`FirstHeaderLine` seul.

**Le rapporteur du CLI** — `scriba -c` avait le même défaut, et le lanceur
l'avait entériné : en externe il n'exigeait que le code 22 et le diagnostic.
Le CLI passait au rapporteur générique un mot de drapeaux **non initialisé**
(`fErrorFlags`, local de `scribacmd.c`) : selon ce que la pile y laissait,
une erreur d'exécution recevait une page CGI complète ou rien du tout. Le
même défaut, mais à pile variable.

Il a désormais son propre rapporteur, `cli_CgiReport`, installé par
`scriba_SetReportFunction` quand `-c` est donné, et un crochet de sortie
standard (`cli_CgiStdOut`) qui retient qu'un octet est parti. La règle est
celle du serveur : page (`Status: 200 OK`, `Content-Type: text/html`,
`<HTML>`) tant que rien n'est sorti, puis un saut de ligne et le diagnostic
seulement. La page reste sur `stderr`, pointeur de rapport par défaut du CLI.

Une différence assumée : le CLI écrit chaque octet aussitôt, sans tamponner
la première ligne. Pour `err_pending.bas`, dont la première sortie n'a pas de
saut de ligne, `sbhttpd` peut donc encore répondre `500` avec la page, alors
que le CLI a déjà envoyé `debut` et n'ajoute que le diagnostic. Le lanceur
l'exige dans les deux sens : `forbid` interdit `<HTML>` et
`Content-Type: text/html` en externe, `forbid_httpd` y ajoute `HTTP/1.0`, et
`erreur-execution` comme `erreur-module`, qui n'écrivent rien, doivent au
contraire contenir la page et sa ligne `Status: 200 OK`.

**Pas de diagnostic en double** — les deux rapporteurs se partagent le
travail, ils ne se doublent pas. Le moteur ne rapporte qu'au chargement
(lecteur, lexer, analyseur, constructeur) ; `scriba_Run` ne rapporte rien, il
rend le code. L'hôte rapporte donc une fois, et `HttpProc` comme le CLI
sortent dès qu'un chargement échoue, sans rapporter à leur tour — le serveur
le dit en commentaire : « error was already reported, just return ».
Mesuré en `scriba -c` sur les cinq échecs du jeu et sur un lot de programmes
fautifs (`open` sur un fichier absent, `return` sans `gosub`, `include`
introuvable, erreur de syntaxe, module absent, fonction de module inconnue,
`cgi::SaveFile`) : jamais deux fois le même diagnostic, jamais deux pages.

Le lanceur le compte désormais (`duplicate_report_problems`) : le diagnostic
attendu doit apparaître une fois et une réponse ne porte qu'un `<HTML>`.
Contrôles négatifs : un second rapport côté CLI, puis un second côté serveur,
font tomber `--cgi-post` à 15/22 en nommant « diagnostic en double » — plus
« page d'erreur en double » quand `REPORT_F_FRST` est remis à zéro entre les
deux.

**Portée** — les erreurs survenant avant la première écriture, celles de la
seizième passe, gardent leur `500` et leur page côté serveur. Les deux autres
hôtes du rapporteur, `stndlone.c` et `variations/standalone/libscriba.c`,
passaient eux aussi un mot non initialisé : il est remis à zéro, faute de
quoi un bit `0x1` laissé par la pile faisait apparaître une page CGI dans un
programme de console. Ils ne connaissent pas `-c`, donc rien d'autre n'y
change.

## E28

**Symptôme** — `open "." for directory as #1` passait l'analyse, puis
échouait à l'exécution avec l'erreur 22 (« file cannot be opened ») ; le
`nextfile(1)` suivant plantait ([E26](#e26)). Seule la forme complète
`open directory "." pattern "*.bas" option 0 as 1` fonctionne, alors que
`file.c` s'annonce comme `OPEN DIRECTORY dir_name PATTERN pattern OPTION
option AS dn` avec des clauses présentées comme optionnelles.

**Cause** — `ex_IsCommandOPEN` acceptait n'importe quel mot après `FOR` et le
recopiait comme mode ; `COMMAND(OPEN)` ne connaît pas `directory`, retombait
sur un `fopen` du nom et rendait 22 plus tard.

**Correctif** — liste blanche des modes dans l'analyseur (`socket`, `input`,
`output`, `append`, `random`, `binary` et leurs variantes `_binary`) : tout
autre mot est une erreur de syntaxe (`0x77`) à l'analyse. C'est la règle
« un refus à l'analyse vaut mieux qu'un refus à l'exécution ».

**Couverture** — `tests/refus_directory.bas`, exécuté par `run.py` dans une
table `REFUS_ANALYSE` qui attend `error &H77` et interdit toute exécution.

**Portée** — l'abréviation `for directory` n'est pas devenue un alias : la
seule forme est celle documentée. `open "x" for wibble as 1` est refusé de la
même façon, au lieu d'ouvrir un fichier puis d'échouer en 22.

## E30

**Symptôme** — `formatdate("%Y-%m-%d")` rendait `"%Y-%m-%d"`, sans erreur :
un motif écrit pour `strftime` passait pour un résultat.

**Cause** — le langage de format est verbal (`YEAR`, `MON`, `DD`, `HH`…,
voir le commentaire de `COMMAND(FORMATDATE)`) ; tout caractère non reconnu
est un littéral, `%` compris. Une faute de format était donc indistinguable
d'un texte voulu.

**Correctif** — un `%` suivi d'une lettre ou d'un chiffre rend
`COMMAND_ERROR_INVALID_TIME_FORMAT` (48, `&H30`), l'erreur que le module
déclare pour ce cas. Un `%` final (`"100%"`) reste un littéral.

**Couverture** — `tests/commandes.bas` (motif refusé, `%` final conservé,
`YEAR` intact) et `tests/manuel.bas`.

**Portée** — les autres fautes de frappe (`"YYYY"`) restent du texte
littéral : le langage n'a pas de joker de directive.

## E31

## E32

**Symptôme** — `pi()` rendait 3.1415926 : huit chiffres. `rad2deg(pi())`
donnait 179.99999989 au lieu de 180, et `sin(pi())` valait 6.5e-9 au lieu de
zéro à la précision machine.

**Cause** — la constante du fichier était une valeur décimale recopiée à la
main, pas `M_PI` ni `4*ATN(1)`.

**Correctif** — `SBPI` porte la constante du double (3.1415926535897931), seule
source de pi de `mathfunc.c` ; les quinze fonctions trigonométriques et les
deux conversions s'en servent.

**Couverture** — `tests/trig.bas` : `rad2deg(pi())` = 180, `rad2deg(pi()/2)` =
90, `round(sin(pi()),12)` = 0.

**Portée** — un programme qui dépendait des huit chiffres historiques voit un
résultat plus juste, pas un résultat différent en nature. `build_tcc` et le
`MANUEL.md` de §11.2 gardent l'ancienne valeur.

## E33

**Symptôme** — `3000000000` valait -2147483648 sous Windows, et
`1000000*10000` valait 1410065408 au lieu de 1e10.

**Cause** — deux chemins distincts, une même ignorance de la plage. Le lexer
accumulait le littéral dans un `double` puis le convertissait en `long` sans
regarder s'il tenait. L'opérateur `*` calculait le produit en entier, donc le
débordement était indéfini en C, et la vérification qui suivait
(`lResult/lop1 == lop2`) était supprimée par le compilateur, libre de supposer
qu'un débordement signé n'arrive jamais.

**Correctif** — le lexer rend un réel quand le littéral dépasse la plage ;
`multiplyLongExact()` teste les opérandes avant de multiplier, par division, et
bascule en réel quand le produit ne tient pas.

**Couverture** — `tests/nombres.bas`, 19 vérifications, dont les valeurs
ci-dessus et les bornes `imax()` et `imin()`.

**Portée** — un littéral qui tient donne toujours un entier, et `1000*1000`
reste un entier : seuls les cas qui débordaient changent, et ils cessaient
d'être justes. Contrôle négatif : réinstaller l'ancien test de produit et
l'ancienne conversion fait tomber `nombres.bas` à 13 échecs sur 19.

## E34

**Symptôme** — `sqr`, `pause` et `fork` étaient acceptés à l'analyse puis
refusés à l'exécution (`error &H1c`), et quinze fonctions trigonométriques
(`tan`, `tan2`, `secant`, `cosecant`, `cotan`, `cotan2`, `hsin`, `hcos`,
`htan`, `hsecant`, `hcosecant`, `hctan`, `actan`, `asecant`, `acosecant`)
figuraient dans la table des symboles avec un corps qui valait
`NOTIMPLEMENTED`.

**Cause** — les blocs `COMMAND` avaient été portés depuis l'amont sans leur
code, et la grammaire les listait déjà.

**Correctif** — les quinze fonctions sont construites (`mathfunc.c`), `sqr`
devient `sqrt` (seul nom gardé), et `pause` comme `fork` quittent la
grammaire : refus à l'analyse, comme le proposait l'audit §2.2. Le compte de
commandes acceptées-puis-refusées est passé de dix-sept à **zéro**.

**Couverture** — `tests/trig.bas` pour les quinze fonctions et les deux
conversions ; `tests/refus_pause.bas`, `tests/refus_fork.bas` et
`tests/refus_sqr.bas` pour les retraits, comptés comme refus attendus par
`tests/run.py`. Les deux autres familles retirées par la quatrième passe ont
elles aussi leur refus : `tests/refus_operateur.bas` pour les 256 opérateurs
morts (`==` en est un) et `tests/refus_cv.bas` / `tests/refus_mk.bas` pour
`cvd`… et `mkd`…, qui n'étaient jusqu'ici vérifiés qu'à la main.

**Portée** — un programme qui appelait `sqr` échoue désormais à l'analyse avec
`error &H68` (fonction inconnue) au lieu de produire une erreur d'exécution.
C'est le but : un refus à l'analyse vaut mieux qu'un refus silencieux à
l'exécution. `build_tcc` garde les anciennes formes.

## E35

**Symptôme** — cinq noms que l'amont acceptait ne passaient plus : `time()`
répondait `error &H68`, et `ucase$`, `lcase$` (ainsi que `upper$`/`lower$`,
déjà présents) n'existaient pas comme formes suffixées. Un programme écrit pour
ScriptBasic d'origine cessait donc de fonctionner sans qu'on touche à sa
grammaire.

**Cause** — la table des noms de `syntax.c` avait perdu ces entrées pendant la
réécriture de la grammaire ; la ligne d'arité de `time` était restée, ce qui
faisait croire que le nom existait.

**Correctif** — `{ "time", CMD_NOW }`, `{ "ucase$", CMD_UCASE }` et
`{ "lcase$", CMD_LCASE }` sont rétablis, à côté de `now`, `ucase` et `lcase`.

**Couverture** — `tests/commandes.bas` §8 : `time()` suit `now()`, et
`ucase$`/`lcase$`/`upper$`/`lower$` rendent le même résultat que leur nom
canonique.

**Portée** — aucun nom retiré volontairement (la famille `cv*`/`mk*`,
`pause`, `fork`, `sqr`) n'est rétabli. `elif` et `elsif` restent absents ;

formes depuis [E37](#e37).

## E36

**Symptôme** — `print ucase("ab")` affichait `AB`, puis `print "ab"`
affichait aussi `AB`. Toute la suite du programme voyait le littéral en
majuscules, y compris dans un autre sous-programme.

**Cause** — `UCASE` et `LCASE` écrivaient dans le tampon de leur argument
(`RESULT = Op1`) au lieu de rendre une nouvelle chaîne. Pour un littéral, ce
tampon est la constante du programme, partagée par toutes ses occurrences :
la première conversion la modifiait définitivement.

**Correctif** — les deux fonctions allouent `NEWMORTALSTRING` et copient les
caractères convertis, comme le faisaient déjà `TRIM`, `LTRIM`, `RTRIM`,
`STRREVERSE` et `CHOMP`.

**Couverture** — `tests/commandes.bas` §8 : après `ucase("ab")`, le littéral
`"ab"` est comparé à `chr(97) & chr(98)`, construit à l'exécution ; l'ancien
code échouait sur ce contrôle, le nouveau passe.

**Portée** — une variable passée à `ucase`/`lcase` n'est plus modifiée sur
place, ce qui était déjà le comportement documenté (« rend une chaîne ») et
celui de toutes les autres fonctions de chaîne.

## E37

**Symptôme** — `if … alors … else …` sur une seule ligne était refusé à
l'analyse (`error &H74`/`&H77`). La forme `if condition THEN commande` sans
`ELSE`, elle, fonctionnait depuis toujours.

**Cause** — deux limites de la même construction. D'abord, `ELSE` et `ELSEIF`
n'avaient qu'une règle qui exige la fin de la ligne juste après le mot-clé :
un `else` suivi d'une commande ne pouvait donc être reconnu. Ensuite, la forme
d'une ligne n'était pas une vraie construction : `SLIF` sautait « la commande
suivante » (`NodeList.rest` de la ligne suivante) sans aucun label de saut,
si bien qu'un `ELSE` n'avait nulle part où s'accrocher et que la branche
affichée était toujours la première.

L'audit initial disait que l'amont acceptait cette forme : **c'est faux**, et
la vérification est facile. `ex_IsCommandIF()` de l'amont refuse
expressément `ELSE`, `ELSEIF` et `ENDIF` derrière le `THEN` d'une forme d'une
ligne, et sa documentation dit « There is no way to specify any ELSE part for
the command in the single line version ». La forme étendue est donc une
extension du dépôt, pas un retour à l'amont.

**Correctif** — la forme d'une ligne est devenue une vraie construction, avec
les mêmes labels que la forme multi-ligne :

- `ex_IsCommandIF()` émet `CMD_SLIF` avec `[condition, label]` et pousse le
  label de la branche sur la pile de compilation ;
- le corps de la branche peut se terminer sur `ELSE`/`ELSEIF` au lieu du
  retour à la ligne (`fSingleLineIFBody` dans le lecteur de règles) ;
- `ELSE` et `ELSEIF` sont analysés par `ex_IsCommandELSE()` et
  `ex_IsCommandELSIF()`, qui acceptent la forme seule sur sa ligne (bloc) et
  la forme suivie d'une commande (une ligne), et émettent `CMD_ELSE_SL` /
  `CMD_ELSIF_SL` dans le second cas ;
- `ex_Command_l()` ferme la construction à la fin de la ligne physique : le
  label resté sur la pile passe dans la liste d'attente et reçoit le nœud de
  la commande suivante ;
- `COMMAND(SLIF)` exécute la même boucle de saut que `COMMAND(IF)`, mais ne
  reconnaît comme marqueurs que ses propres `ELSE_SL`/`ELSIF_SL`. Un `ELSE`
  de bloc englobant reste pour elle une simple cible de saut, ce qui évite
  qu'un `if` d'une ligne placé en fin de corps saute dans le `else` du bloc.

**Règle de la forme d'une ligne** — une commande exactement par branche, et
la construction entière sur une seule ligne physique. Les commandes qui
ouvrent une construction de plusieurs lignes (`IF`, `FOR`, `WHILE`, `REPEAT`,
`SUB`, `FUNCTION`, les déclarations) sont refusées à l'analyse dans une
branche, tout comme le mélange des deux formes :

```basic
if 1 then
  print "a"
elseif 1 then print "b"   ' refusé : la chaîne d'une ligne se ferme ici
end if
```

**Couverture** — `tests/slif.bas`, 30 vérifications : branches vraie et
fausse, chaînes de trois `ELSEIF`, arrêt à la première branche vraie,
conditions `undef`/chaîne vide/chaîne non vide, imbrication dans un bloc, une
boucle et un `WHILE`, `ELSE` de bloc non pris par un `if` d'une ligne, `GOTO`
et `CALL` comme branches. Deux refus : `refus_slif_for.bas` (`FOR` dans une
branche) et `refus_slif_mix.bas` (mélange des formes).

**Portée** — `elif`, `elsif` et `else if` restent absents, comme décidé à la
passe des commandes mortes : l'amont les avait, le dépôt ne les a plus, et
les rétablir demande une entrée de nom par variante ; `elseif` couvre le
besoin. Les deux formes d'une ligne et multi-ligne ne se mélangent pas dans
une même construction.

## E38

**Symptôme** — après un changement d'en-tête (`expression.h`, `syntax.h`),
`python build.py --target windows-x64` réussissait en quelques secondes, puis
le binaire plantait sur n'importe quel programme, `print "hi"` compris :
violation d'accès, sans le moindre message de compilation.

**Cause** — `build.py` ne recompilait un objet que si son `.c` était plus
récent que lui. Un `.h` modifié ne déclenchait donc rien : des objets anciens
et des objets neufs se retrouvaient liés ensemble, alors que les structures
(`eXobject`, `ExecuteObject`, `NUM_CMD`) n'avaient plus la même taille selon
le fichier. Le binaire lisait des champs décalés.

**Correctif** — `newest_header_mtime()` rend la date du plus récent
`src/**/*.h` ; les trois constructeurs (programme, moteur `re`, modules)
recompilent tout objet plus ancien. `--clean` reste la voie sûre quand on
doute de l'état de `obj/`.

**Couverture** — `touch src/expression.h` puis
`build.py --target windows-x64` : les objets du coeur sont recompilés (leur
date dépasse celle de l'en-tête) et `tests/run.py` rend 17/17. Avec l'ancienne
règle, le même enchaînement laissait un binaire qui plantait sur `print "hi"`.

## E39

**Symptôme** — un `do … loop` sans condition après `LOOP` était refusé à
l'analyse (`error &H74: erroneous nesting of constructs…`), alors que
`loop while` et `loop until` passaient. `exit do` ne trouvait de son côté
aucun label à quitter.

**Cause** — la tête `DO` pousse deux labels de type `CMD_LOOP` (`GO_FORWARD`
puis `COME_BACK`), mais la règle `LOOP` nue les attendait en `CMD_DO`.
`_ex_PopLabel()` ne compare que le type du sommet de la pile, et le tableau
`GoConstant` d'une règle ne contient que la constante écrite dans
`syntax.c` : la comparaison échouait donc à chaque tour. Le défaut était
masqué par la couverture, `tests/loops.bas` ne fermant qu'avec `loop while`.

**Correctif** — la règle `CMD_LOOP` attend désormais `CMD_LOOP`, comme
`LOOP WHILE` et `LOOP UNTIL` le faisaient déjà. `EXIT DO` ramène `CMD_DO` et
`CMD_LOOP` à une seule espèce de boucle, puisque la construction porte deux
types de labels différents.

**Couverture** — `tests/exit.bas` exécute un `do … loop` nu et en sort par
`exit do` ; les formes `loop while` et `loop until` sont inchangées.
C'est le défaut trouvé pendant la passe `EXIT` (voir
[EVOLUTIONS.md](EVOLUTIONS.md#2026-10-25--vingt-deuxième-passe--exit-quitte-les-boucles)).

**Symptôme** — `odbc` ne se lie pas pour linux : `unable to find dynamic

## E43

**Symptôme** — `curl::escape` et `curl::unescape` corrompaient le tas

**Couverture** — `tests/curl.bas` (aller-retour escape/unescape), qui
plantait avant correction et passe depuis.

## E44

**Symptôme** — le harnais `tests/manuel.bas` échoue sous Linux sur cinq
affirmations : `maxint` rend 9223372036854775807 (attendu 2147483647),
`minint` rend 0, le test d'intervalle de `rnd` rend faux, `randomize`

harnais tourne 156/156 sur windows-x64 et windows-x86. L'harmonisation
(valeurs d'ABI par fonctions dédiées, politique par plateforme) est
remise à la passe langage — [PLAN.md](PLAN.md), phase 8.

## E46

**Symptôme** — en CI (ubuntu), `--cgi-post` échouait sur les cas à code
étendu avec « code 8, 524296 attendu », et la page d'erreur portait un
`%s` brut (`Extension specific error: %s`) au lieu du texte du module.

**Cause** — deux défauts distincts qui se masquaient l'un l'autre :

1. le code de sortie : `exit()` POSIX ne transmet que 8 bits —
   `exit(0x00080008)` rend 8 sous Linux, 524296 sous Windows (exit 32
   bits). Le code complet, lui, est affiché par le rapporteur ;
2. le message : `pEo->pszModuleError` n'était rempli que sur le chemin
   des appels de fonction (`commands/external.c`) ; une erreur rendue
   par `bootmodu` (exactement les refus FILE_MAX/CONTENT_MAX, qui tombent
   au démarrage du module) arrivait au rapporteur sans son texte, sur
   les deux plateformes — Windows passait parce que la campagne n'y
   exigeait que le code.

**Correctif** — `modu_LoadModule` (modumana.c) interroge `emsgmodu` du
module après un bootmodu en erreur, selon le pattern d'external.c, si
bien que le texte réel du module (« File is larger than the configured
allowed size. »…) remplace le repli ; la campagne relit le code complet
dans la page (`error 0x........`) quand le code de sortie POSIX ne peut
pas le porter.

**Couverture** — `--cgi-post` 22/22 sur windows-x64 ET linux-x64 (WSL) ;
la CI rejoue les deux cibles (restriction retirée du workflow). Les
`EXPECT_HTTPD` de `tests/run.py` exigent désormais les textes du module.

**Portée** — un programme qui dépendait du repli « program terminated
with error » voit le texte du module : plus d'information, pas moins.

**Symptôme** — en CI (macos-arm64, Apple Silicon natif), le test du
